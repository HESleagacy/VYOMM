# VYOMM Operating Modes

> **Status:** DRAFT — metric names marked "unverified" need live-cluster discovery
> per `METRICS_CONTRACT.md` before use in dashboards or recording rules.

VYOMM operates in three modes, selected via `VYOMM_ENVIRONMENT_MODE` in `.env`.
Each mode has a different fidelity level. This document records exactly what
each mode proves and does not prove.

---

## Mode: `trial`

**No GPU, no Kubernetes required for the simplest path.**

| Property | Value |
|----------|-------|
| Kubernetes | Optional — kind cluster with [fake-gpu-operator](https://github.com/run-ai/fake-gpu-operator) |
| Real GPU | None |
| HAMi components | Scheduler only (`devicePlugin.enabled=false`) |
| GPU simulation | fake-gpu-operator simulates `nvidia.com/gpu` capacity on CPU nodes |
| DCGM exporter | Simulated — fake-gpu-operator deploys a fake `nvidia-dcgm-exporter` |
| VYOMM telemetry | Synthetic, generated by Go simulator with deterministic seeds |
| Source tag | `source: "synthetic"`, `mode: "trial"` |

### What trial mode proves

- VYOMM's API endpoints work end-to-end (telemetry ingest → anomaly → incident → runbook)
- HAMi scheduler component starts and intercepts pod scheduling (when kind cluster is used)
- fake-gpu-operator makes Kubernetes report `nvidia.com/gpu` on CPU-only nodes
- The complete dashboard rendering flow works with synthetic data
- Provenance badges correctly display `synthetic / trial`

### What trial mode does NOT prove

- HAMi device-plugin GPU registration — disabled in trial mode
- `nvidia.com/gpumem` memory slicing — fake-gpu-operator doesn't support it
- `nvidia.com/gpucores` compute limits — fake-gpu-operator doesn't support it
- CUDA program execution — no real or mocked CUDA runtime
- Real DCGM GPU metrics — the exporter is simulated, always returns 0
- Physical memory or compute isolation

### Known DCGM metrics from fake-gpu-operator (from tutorial, needs live verification)

The simulated DCGM exporter produces at minimum:
- `DCGM_FI_DEV_GPU_UTIL` (confirmed in Lab 2 tutorial, value = 0)

Other DCGM metric names must be discovered from a live scrape, not assumed.
See `docs/hami-design-spec.md` §5.3 for the discovery procedure.

## Mode: `nvml-mock`

**HAMi scheduler + device-plugin running against mocked NVIDIA devices inside
a kind cluster.**

| Property | Value |
|----------|-------|
| Kubernetes | Required — kind cluster |
| Real GPU | None |
| HAMi components | Full: scheduler + device-plugin (built from `main` branch) |
| GPU simulation | [nvml-mock](https://github.com/NVIDIA/k8s-test-infra) provides fake `libnvidia-ml.so`, `/dev/nvidia*`, PCI topology for 8× A100 GPUs |
| DCGM exporter | Not deployed by default (add Prometheus stack separately if needed) |
| VYOMM telemetry | Synthetic, generated by Go simulator with deterministic seeds |
| Source tag | `source: "synthetic"`, `mode: "nvml-mock"` |

### What nvml-mock mode proves

- **HAMi scheduling/allocation semantics work end-to-end:**
  - Device-plugin discovers 8 A100 GPUs via NVML API
  - Each physical GPU is sliced into 10 virtual slots (80 total `nvidia.com/gpu`)
  - Pods requesting `nvidia.com/gpu` get scheduled by `hami-scheduler`
  - `hami.io/vgpu-devices-allocated` annotation is correctly written with UUID, vendor, memory, cores
- **GPU sharing (time-slicing)** — multiple pods share the same physical GPU
- **Memory budget tracking** — `nvidia.com/gpumem` and `nvidia.com/gpumem-percentage` are correctly parsed by the scheduler and recorded in allocation annotations
- **Core percentage limits** — `nvidia.com/gpucores` values are recorded in allocation annotations
- **Multi-GPU allocation** — pods requesting >1 GPU get multiple allocation entries
- **VYOMM's `vyomm_scheduler_allocation_events_total` metric can track allocation lifecycle**
- **VYOMM's `vyomm_hami_scrape_success` gauge reflects scheduler endpoint reachability**

### What nvml-mock mode does NOT prove

- **CUDA execution** — no real CUDA runtime; pods use `CUDA_DISABLE_CONTROL=true`
- **Physical memory enforcement** — HAMi's `hami-core` library cannot enforce memory limits without a real GPU
- **Physical compute enforcement** — core percentage limits are annotation-only, not enforced
- **Real DCGM metrics** — no DCGM exporter is deployed; `DCGM_FI_DEV_GPU_TEMP`, `DCGM_FI_DEV_GPU_UTIL`, etc. are not available
- **vgpu-monitor health** — the sidecar crashes (1/2 READY is expected) because it needs real GPU monitoring infrastructure
- **Memory overcommit, memory analysis, memory override features**
- **Driver compatibility** — nvml-mock simulates driver 550.163.01; real driver behavior may differ

### nvml-mock VYOMM integration points

VYOMM observes nvml-mock mode via:

1. **Pod annotations** — `hami.io/vgpu-devices-allocated` on scheduled pods
2. **HAMi scheduler endpoint** — `hami-scheduler` Service port 31993
3. **Kubernetes events** — `FilteringSucceed`, `BindingSucceed` events from `hami-scheduler`

Metric names from the HAMi scheduler endpoint **have not been verified** from a
live scrape. The Controller must run the discovery procedure in
`docs/hami-design-spec.md` §5.3 before recording any HAMi metric names in
dashboards or recording rules.

## Mode: `real-gpu`

**Real NVIDIA GPU with real HAMi installation.**

| Property | Value |
|----------|-------|
| Kubernetes | Required — any cluster with NVIDIA GPUs |
| Real GPU | Required — NVIDIA GPU with driver v440+ |
| HAMi components | Full: scheduler + device-plugin from Helm chart |
| GPU simulation | None — real hardware |
| DCGM exporter | Real — from NVIDIA GPU Operator or standalone |
| VYOMM telemetry | Mix of real HAMi/DCGM metrics and VYOMM application metrics |
| Source tag | `source: "real"`, `mode: "real-gpu"` |

This mode is out of scope for Phase 4. See `docs/real-gpu-validation.md` for
the validation plan.
